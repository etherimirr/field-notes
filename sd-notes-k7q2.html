押题 · 按可能性排序

依据是他们招聘启事里列的五件事，加上两位面试官的背景（都做云安全图）。每题给：他们大概会怎么说、像书里哪一章、三句话的答题骨架、去哪里看完整答案。

押题 1（最可能）· 持续同步客户的云资源，做成一张接近实时的图

Design a system that keeps an up-to-date map of a customer's cloud environment.

  • 像哪一章：第 9 章爬虫，加第 4 章限流。
  • 骨架：① 调度器按租户发任务，Worker 用只读角色去列资源。② 写图时用 MERGE 并盖上本轮编号，整轮跑完再清掉没盖到的，这样能发现删除。③ 全量同步保证不漏，云上的变更事件保证新鲜，限流器保证不打爆客户的额度。
  • 必被追问：删除怎么发现；同步到一半失败怎么办；怎么不影响客户生产；大租户怎么并行。
  • 看哪里：图 1，以及第二部分的「主答案」和「深挖八处」。

押题 2 · 判断一个漏洞到底危不危险

We get thousands of CVEs from scanners. How would you decide which ones actually matter?

  • 像哪一章：书里没有原题。结构上借第 11 章「预先算还是现算」。
  • 骨架：① 把漏洞清单挂到图里对应的机器或镜像上。② 危险等于三件事同时成立：公网走得到、漏洞真的在、几步之内有敏感数据。每件都是图上的一段路径查询。③ 路径查询贵，所以每轮同步后预先算好并存分数，页面直接读。
  • 必被追问：路径太多怎么办（限制步数、先从「暴露在公网」的点出发）；怎么定义敏感数据（标签加规则）；误报怎么处理。
  • 看哪里：图 2，第二部分「备用题 A」。

押题 3 · 让 AI agent 又快又准地回答关于图的问题

How would you let an LLM agent answer questions about the graph, quickly and correctly?

  • 像哪一章：第 13 章的思路：贵的计算离线做好，在线只查现成的。
  • 骨架：① 不让模型自由写查询，而是给它一组有限的工具（查某个资源、查两点之间的路径、列某类风险），每个工具背后是写好的、带租户号和步数上限的查询。② 把图的结构说明（有哪些点、哪些线）放进提示里，常问的问题缓存结果。③ 用一批标准问题做评测集，每次改动都跑一遍，看准确率和耗时。
  • 必被追问：模型编造怎么办（答案必须带上查询结果里的资源 ID）；慢怎么办（限制步数、缓存、预先算）；权限怎么管（工具层强制租户号）。
  • 看哪里：第二部分「备用题 B」。

押题 4 · 给图加「时间旅行」，能回放一次攻击

How would you add time travel to the graph, so we can see what it looked like last Tuesday?

  • 像哪一章：第 15 章网盘的版本历史。
  • 骨架：① 不每轮存一整张图，只记变化：每个点和线带「从哪一轮开始有」和「到哪一轮没了」两个编号。② 查过去某一刻，就是筛出「开始 ≤ 那一刻 < 结束」的点和线。③ 太旧的历史压缩后搬到便宜的存储，并限制保留多久。
  • 必被追问：存储涨多快（只有变化才写，大部分资源不变）；属性变了算不算新版本（算，关一条开一条）；查询会不会变慢（给两个编号建索引）。
  • 看哪里：借来的零件 表里「时间旅行」那一行，第 15 章。

押题 5 · 推断一个资源归谁管

How would you figure out who owns a given cloud resource?

  • 像哪一章：书里没有原题。数据流像第 13 章：日志 → 聚合 → 离线算好 → 在线查。
  • 骨架：① 收集几类证据：谁创建的（操作记录）、资源上的标签、它是哪份 Terraform 代码建的、谁最近改过。② 每类证据给一个权重，加起来给出「最可能的负责人」和把握有多大。③ 把握低的标出来让人确认，人确认过的结果优先级最高，并反过来校准权重。
  • 必被追问：创建人离职了怎么办（映射到团队而不是个人）；证据互相矛盾怎么办（展示证据，让人选）。

第一部分 · 先看这五张图（各 1 分钟）

图 1 · 最可能的题：持续同步客户的云资源，画成一张图

照着数字讲：① 调度器到点发任务 ② Worker 领任务 ③ 戴着客户给的只读帽子去云上「点名」 ④ 把整理好的数据交给写图器 ⑤ MERGE 进 Neo4j，并盖上这一轮的编号；没盖到编号的就是云上已删的，清掉 ⑥ 用户或 AI agent 提问 ⑦ 查询 API 带着租户号去图里走路径。虚线是辅助：限流器管住调用速度，事件流让「有变化」时不用等下一轮。

  • 为什么要队列：一个租户同步失败不拖累别的租户；Worker 可以随便加机器。
  • 为什么要 update tag：云的接口只告诉你「现在有什么」，不告诉你「什么被删了」。盖章再清理，就能发现删除。
  • 为什么全量加事件两条路：全量慢但不会漏；事件快但可能丢。两条一起，事件管新鲜，全量管兜底。
  • 半路失败怎么办：这一轮没跑完就不要清理，否则会把没来得及点到名的资源误删。

A scheduler enqueues one job per tenant and module. Workers assume a read-only role, list resources, and MERGE them into the graph with this run's update tag. After a complete run, cleanup removes anything without the current tag. Events give freshness, full syncs give correctness.

图 2 · 备用题：一个漏洞到底危不危险

危险等于三件事同时成立：公网能走到这台机器、机器上真有这个漏洞、从机器能一路走到敏感数据。每一件都是图上的一段路。

Severity alone isn't risk. I'd rank a finding by three things: is it reachable from the internet, is the vulnerable package actually there, and what sensitive data sits within a few hops.

图 3 · 限流器（书第 4 章，Subimage 调云接口一定用得上）

  • 令牌桶：桶里每秒补固定数量的令牌，来一个请求拿走一个，没令牌就拒绝或等。允许短时间突发。
  • 多台机器共用一个计数，就放 Redis，用原子操作，避免两台同时读到「还剩 1 个」。
  • Subimage 的特别之处：额度是客户的，要按「客户账号 × 服务 × 区域」分别限，遇到 Throttling 就指数退避。

图 4 · 通知系统（书第 10 章：发现风险后怎么告警）

  • 每个渠道一条队列，Slack 挂了不影响邮件。
  • 先去重再发：同一个风险同一天只提醒一次。
  • 发送失败就重试，重试几次还不行进「死信队列」等人看。

系统设计面是怎么回事

他们给一个开放的题目（比如「设计一个系统，持续同步客户的云资源」），你边说边画，他们不断追问。没有标准答案。他们看的是：你会不会先问清楚、能不能把大问题拆开、知不知道哪里会坏、会不会做取舍。两位都是这个领域的专家，所以别背书，多问他们的真实约束。

六步流程（照这个顺序走，别一上来就画框）

步骤大约时间做什么开口的那句话
1 问清需求5 分钟谁用、读还是写多、要多新鲜、多大规模“Before I design anything, can I ask a few questions about scale and freshness?”
2 估数量3 分钟多少租户、多少资源、多久同步一次“Let me put rough numbers on this so the design fits.”
3 画大图8 分钟五六个框：调度、队列、采集、写图、查询“Here's the simplest version that works. Then I'll go deeper where it's risky.”
4 深挖两三处25 分钟他们指哪你挖哪；没指就挖「删除」和「限流」“Which part would you like me to go deeper on? Otherwise I'll start with deletes.”
5 讲会怎么坏8 分钟失败、重试、监控“Let me walk through what happens when a sync fails halfway.”
6 收尾3 分钟总结取舍，说还会做什么“To summarize the trade-offs I made…”
三个随时能用的句子：
· 想一下再答：“Let me think about that for a few seconds.”
· 不确定：“I'm not sure how Neo4j handles that. My assumption is X. Is that right?”
· 做取舍：“There are two options. A is simpler but B scales better. I'd start with A because we're small, and move to B when we see this metric.”

概念从零讲（开场前看 5 分钟）

图数据库

普通数据库存的是表。图数据库存的是「点」和「线」。点是东西（一台机器、一个账号、一个数据库），线是关系（这台机器「可以扮演」这个角色，这个角色「可以读」这个数据库）。打个比方：表像通讯录，图像一张地铁线路图。问「从 A 站换几次车能到 B 站」，在线路图上顺着线走就行；在通讯录里就得一张表一张表地连，连五六次就非常慢。

A graph database stores nodes and relationships. Multi-hop questions like “can this machine reach that database” are a path walk, not five joins.

Cypher（Neo4j 的查询语言）

写法像画图：圆括号是点，方括号是线。

// 找出能从公网访问、又能一路走到敏感数据库的机器，最多走 4 步
MATCH p = (i:EC2Instance {exposed_internet: true})
          -[*1..4]->(d:RDSInstance {sensitive: true})
RETURN p LIMIT 25;

MERGE 的意思是「有就更新，没有就创建」，所以同一条数据写两遍也只有一个点。这就是幂等。

Cartography 的同步模型（他们的看家本领，一定要懂）

每个数据源一个模块（AWS、GCP、Okta、GitHub……）。每个模块做三步：取（调云厂商的接口把资源列出来）、整理（变成统一格式）、写（MERGE 进图里）。

关键的小设计：每一轮同步有一个编号，叫 update tag。这一轮写到的每个点和每条线，都盖上这个编号。同步完之后跑「清理」：凡是编号不是这一轮的，说明这一轮没看到它，也就是云上已经删了，把它从图里删掉。

比方：老师点名。点到的人在名单上打个今天的勾。点完之后，没有今天这个勾的人，就是没来的。

Each sync run stamps everything it sees with an update tag. Afterwards, cleanup deletes whatever doesn't carry the current tag. It's mark and sweep.

IAM、角色、AssumeRole

IAM 是云上的权限系统。「角色」是一顶帽子，戴上就有某些权限。AssumeRole 是「我戴上你的帽子」。客户给 Subimage 一顶只读的帽子，Subimage 戴上它去客户的账号里读资源清单。攻击路径很多就是「A 能戴 B 的帽子，B 能戴 C 的帽子，C 能读数据库」这样一串。

限流和退避

云厂商限制你每秒能调多少次接口，超了就报 Throttling。客户自己的自动化也在用同一份额度，所以你调太猛会影响客户的生产。做法：令牌桶（每秒发固定数量的令牌，有令牌才能调）加指数退避（失败了等 1 秒、2 秒、4 秒再试，每次加一点随机，免得大家同时重试）。

Token bucket to cap the rate, exponential backoff with jitter on throttling errors.

多租户

一套系统服务很多家客户，每家是一个租户。安全产品最怕的是 A 客户看到 B 客户的图。隔离方式从弱到强：每条查询带租户号 → 每个租户一个独立的数据库 → 每个租户一台独立的机器。

主答案：设计一张接近实时、自动更新的云资源地图

这是最可能的题，也是他们 JD 的第三条。别的题也能从这个答案里拆零件用。

第 1 步 · 先问这些

  • “How many tenants, and how big is a large one? Thousands of resources, or millions?”
  • “How fresh does the map need to be? Hourly, or within a minute for some resources?”
  • “Which sources first: only AWS, or also identity and code?”
  • “Is the read side mostly the UI and the agent, or also bulk exports?”
  • “Do we only have read-only access in the customer's account?”

第 2 步 · 估数量（说出来，别心算）

Let me assume a few hundred tenants. A large tenant has about one million resources across around a hundred cloud accounts, and three to five relationships per resource, so three to five million relationships. A full sync every hour. If one list call returns about a hundred resources, a full pass is about ten thousand list calls per hour, around three per second on average. That average is fine. The risk is bursts against one service in one account, so rate limiting has to be per account and per service.

假设几百个租户。大租户大约 100 万个资源，分布在 100 个左右的云账号里；每个资源 3 到 5 条关系，所以 300 万到 500 万条线。每小时全量同步一次。一次列表调用大约返回 100 个资源，全量一遍大约 1 万次调用，平均每秒 3 次左右。平均值没问题，风险是对某个账号的某个服务突然打一大波，所以限流要按「账号加服务」来做。

第 3 步 · 大图

                 每小时全量                         事件(准实时)
  调度器 ──► 任务队列 ──► 采集 worker          CloudTrail/EventBridge
  (按 租户/账号/              │ 取+整理                │
   地区/服务 拆任务)          ▼                        ▼
                         原始快照(S3) ──► 写入器 ◄── 事件队列 ──► 重新读取这个资源
                                             │ MERGE + update tag
                                             ▼
                                   图数据库(每个租户一个库)
                                             │
                          清理(只在整轮成功后) + 分析任务(标出公网暴露等)
                                             │
                                   API(FastAPI) ──► 界面 / MCP 给 agent

A scheduler breaks each tenant's sync into small tasks: one per account, region and service. Workers pull tasks from a queue, call the cloud APIs with a read-only role, and save the raw responses to object storage. A loader turns them into nodes and relationships and merges them into that tenant's graph, stamping each with this run's update tag. When a full pass succeeds, cleanup removes whatever wasn't seen, and analysis jobs mark things like internet exposure. For freshness between full syncs, cloud audit events tell us which resource changed, and we re-read just that resource.

调度器把每个租户的同步拆成小任务：每个账号、每个地区、每个服务一个。worker 从队列取任务，用只读角色调云接口，把原始返回存进对象存储。写入器把它们变成点和线，合并进这个租户的图，并盖上这一轮的编号。全量成功之后，清理任务删掉这一轮没看到的东西，分析任务标出「暴露在公网」这类标记。两次全量之间要更新鲜，就靠云的审计事件告诉我们哪个资源变了，只重读那一个。

深挖：他们最可能追问的八处

① 删除怎么处理？同步到一半失败了怎么办？（最容易出事的地方）

Deletes are the dangerous part. The cloud doesn't tell you what was deleted in a list call. You only notice it's missing. So I stamp every node with the run's update tag and, after the sync, delete what doesn't have the current tag. The rule I'd be strict about: cleanup for a scope only runs if every task in that scope succeeded. If the EC2 listing for one region failed, I must not conclude those machines are gone. I'd also add a safety check: if a cleanup would delete more than, say, thirty percent of a type, stop and alert instead.

删除是最危险的部分。列表接口不会告诉你什么被删了，你只能发现它「不见了」。所以每个点都盖上这一轮的编号，同步完删掉没有当前编号的。我会死守一条规则：某个范围的清理，只有在这个范围里所有任务都成功时才跑。如果某个地区的机器列表拉失败了，我不能因此认为那些机器没了。再加一道保险：如果一次清理要删掉某类资源的 30% 以上，就停下报警。

② 怎么不把客户的接口额度打爆？

A token bucket per tenant account and service, so EC2 calls in account A never starve account B. On a throttling error, exponential backoff with jitter. I'd also cap concurrency per account and learn the limits over time: if we see throttling, lower that bucket's rate automatically. And I'd keep in mind the quota is shared with the customer's own automation, so we should run below the limit, not at it.

每个「租户账号加服务」一个令牌桶，A 账号的调用不会饿死 B 账号。遇到限流错误就指数退避加随机。每个账号再设并发上限，并且边跑边学：一旦出现限流，自动把那个桶的速率调低。还要记住这份额度是和客户自己的自动化共用的，所以要跑在上限以下，别贴着上限。

③ 任务失败、worker 挂了怎么办？

Every task is safe to repeat, because the loader uses merge on a stable ID, like the resource's ARN. So the queue can redeliver freely. For long listings I checkpoint the pagination token, so a retry resumes instead of starting over. After a few failures a task goes to a dead-letter queue and that scope is marked incomplete, which blocks its cleanup. I did something similar at TikTok: I saved each run's phase and handles in MongoDB so a three-hour job could restart where it stopped.

每个任务都可以安全重跑，因为写入用的是按稳定 ID（比如资源的 ARN）做 MERGE。所以队列可以随便重发。长列表我会存翻页的位置，重试时接着拉，不从头来。失败几次后任务进死信队列，这个范围标成「不完整」，它的清理就被拦住。我在 TikTok 做过类似的事：把每次运行的阶段和句柄存进 MongoDB，3 小时的任务能从断的地方接着跑。

④ 多租户怎么隔离？客户的凭证怎么放？

For a security product I'd isolate strongly: one database per tenant, and a separate instance for the largest customers. Filtering by tenant ID in every query is cheaper, but one missed filter leaks another customer's map. For credentials, we don't store keys. The customer creates a read-only role with an external ID, and we assume it to get short-lived credentials. Queues and rate limits are per tenant too, so one huge tenant can't slow the others.

安全产品我会强隔离：每个租户一个数据库，最大的客户单独一个实例。每条查询里按租户号过滤更便宜，但漏写一次过滤就泄露了别家的图。凭证方面，我们不存密钥：客户建一个带 external ID 的只读角色，我们去扮演它，拿到的是短期凭证。队列和限流也按租户分，一个巨型租户拖不慢别人。

⑤ 每小时一次不够新，怎么做到接近实时？

Use the cloud's audit events as hints. A CloudTrail event says “this security group changed.” I don't trust the event's content as the truth. I use it to trigger a fresh read of that one resource and merge the result. Events can arrive late, twice, or out of order, so re-reading makes it safe. The hourly full sync stays as the backstop that repairs anything we missed.

把云的审计事件当成「提示」。CloudTrail 说「这个安全组变了」，我不把事件内容当成事实，只用它触发对这一个资源的重新读取，再合并进图。事件可能迟到、重复、乱序，重新读一次就都安全了。每小时的全量同步留着兜底，修补漏掉的东西。

⑥ 攻击路径的查询怎么保证快？

Three things. Precompute what's expensive: an analysis job marks nodes as internet-exposed after each sync, so the query starts from a small set. Bound the walk: limit path length to four or five hops and return the top results. And index the properties we start from. For the UI I'd cache the common views per tenant and invalidate them when a sync finishes.

三件事。贵的东西提前算好：每次同步后，分析任务把「暴露在公网」的点标出来，查询就从一小撮点出发。限制走多远：路径最长四五步，只返回最靠前的结果。出发用到的属性建索引。界面上常用的视图按租户缓存，同步完成时让缓存失效。

⑦ 时间旅行：怎么看「上周二的图长什么样」？（JD 里有这条）

Two options. One, put a valid-from and valid-to time on every node and relationship, and filter queries by time. It's simple to query, but the graph keeps growing. Two, keep the live graph as it is and write every change to an append-only log: added, removed, property changed. To see last Tuesday, load the nearest snapshot and replay the log up to that time. I'd start with the change log plus a daily snapshot, because it doesn't slow down today's queries, and replaying an attack is a rare, heavy read that can take a few seconds.

两个方案。一，给每个点和线加「从什么时候有效、到什么时候失效」，查询时按时间过滤。查起来简单，但图会越来越大。二，现在的图保持原样，把每次变化写进只追加的日志：新增、删除、属性改了。要看上周二，就加载最近的一份快照，再把日志回放到那个时间。我会从「变更日志加每天一份快照」开始，因为它不拖慢今天的查询；回放一次攻击是很少发生的重查询，等几秒可以接受。

⑧ 怎么知道系统是健康的？

The number I'd watch is freshness per tenant: how old is the oldest scope that hasn't synced. Then sync duration and failure rate per module, throttling rate per account, and the size of each cleanup. A sudden drop in node count is treated as an incident, not as data.

我最盯的数是每个租户的新鲜度：最久没同步成功的范围有多旧。然后是每个模块的同步耗时和失败率、每个账号的限流比例、每次清理删了多少。点的数量突然掉下去，要当成事故处理，不能当成数据。

备用题 A：一个漏洞到底危不危险

提纲：扫描器报「这个软件包有漏洞」→ 顺着图往上找它跑在哪 → 能不能从公网到 → 它的角色能碰到什么数据 → 排优先级

A scanner gives thousands of findings, and most don't matter. I'd join each finding to the graph: package, to image, to running workload, to network exposure, to the role it runs as, to the data that role can read. Then score it: internet-reachable and can reach sensitive data goes to the top; a vulnerable package in an image nobody runs goes to the bottom. I'd keep the reasons with the score, so an engineer sees the path and doesn't have to trust a number.

扫描器会报几千条，大部分不要紧。我会把每条发现接到图上：软件包 → 镜像 → 正在跑的服务 → 网络暴露 → 它用的角色 → 这个角色能读的数据。然后打分：公网能到、又能碰到敏感数据的排最前；一个没人在跑的镜像里的漏洞排最后。分数旁边留着理由，工程师看到的是那条路径，不用去信一个数字。

备用题 B：让 AI agent 回答关于图的问题（你的强项）

提纲：给 agent 几个工具，不让它随便写查询 → 只读、有超时和条数上限 → 自动带上租户 → 用一套标准问题做评测

I'd expose the graph through an MCP server with a few tools: get the schema, run a named query like “paths from the internet to this resource,” and, last, run read-only Cypher with a timeout and a row limit. Named queries first, because free-form queries are where models make mistakes. The tenant is fixed by the server, never by the model. And I'd build the eval before tuning anything: a set of questions with known answers on a test graph, scored on whether the answer is right and whether the path it cites exists. That's the work I do in my research: checking whether an agent's answer can be trusted.

我会用一个 MCP 服务把图开放出来，给几个工具：取图的结构；跑一个命名好的查询（比如「从公网到这个资源的路径」）；最后才是带超时和条数上限的只读 Cypher。先用命名查询，因为模型最容易在自由查询上出错。租户由服务端定死，绝不由模型决定。调任何东西之前先把评测搭好：在一张测试图上准备一批有标准答案的问题，按「答案对不对、它引用的路径存不存在」打分。这正是我研究里做的事：检查 agent 的回答能不能信。

如果出的是通用题

  • 任务调度器 / 定时任务系统：用上面的「调度器 → 队列 → worker → 状态存库 → 幂等重试 → 死信队列」。你的 TikTok 长任务故事直接用。
  • 限流器：令牌桶；多台机器共享计数用 Redis；说明超限时是拒绝还是排队。
  • 日志或事件采集：队列缓冲、按租户分区、至少一次投递加去重、冷热分层存储。

第三部分 · 通用题库（Alex Xu《System Design Interview》第 1 到 15 章，逐章通读后用自己的话重写）

每章四块：会怎么问，要点，能借到 Subimage 的地方，一句能直接说的英文。图是照书里的结构重新画的。

第 1 章 · 从一台机器长到百万用户

会怎么问：「你的系统用户涨 100 倍怎么办？」任何题的收尾都会用到。

  • 起点：网站、数据库、缓存全在一台机器上。
  • 第一步拆开：Web 一层，数据库一层，各自扩。
  • 加负载均衡：用户只连它，后面的机器用内网地址。一台挂了流量自动去另一台。
  • 数据库主从复制：主库管写，从库管读。主库挂了，提一台从库当主库。
  • 缓存：先查缓存，没有再查库并写回缓存。要定过期时间；缓存满了按「最久没用的先踢」。
  • CDN：图片、脚本这类不变的文件放到离用户近的节点。
  • Web 层无状态：登录状态放到共享存储里，任何一台机器都能接任何请求，才好自动加减机器。
  • 多机房：按用户位置分流；一个机房挂了全部切到另一个。难点是数据同步。
  • 消息队列：生产者往里放，消费者往外取。两边互不等待，队列长了就加 Worker。
  • 数据库分片：按某个键（比如用户号）把数据分到多台。三个坑：以后要重新分片、热点键、跨片不能连表。

借到 Subimage：他们现在 5 个人，一台 Neo4j 够用。说清「现在不分片，等到什么指标再分」比一上来就分片更加分。

I'd keep the web tier stateless, add read replicas and a cache first, and only shard when a single graph database can't hold the data.

第 2 章 · 估算

会怎么问：「大概多少 QPS？要多少存储？」

  • 流程：日活 → 每人每天几次 → 除以 86400 得每秒次数 → 高峰乘 2。
  • 存储：每条多大 × 每天多少条 × 保存几年。
  • 几条常识：内存快、磁盘慢；能不找盘就不找盘；发到网上之前先压缩；跨机房一来一回很慢。
  • 可用性：99.9% 一年坏约 8.8 小时，99.99% 约 53 分钟。
  • 技巧：取整，把假设写下来，写单位。过程比结果重要。

Let me round aggressively and write my assumptions down, so we can correct them together.

第 3 章 · 答题四步

会怎么问：整场面试的骨架。

  • ① 问清需求和范围，3 到 10 分钟。别抢答。问：做哪些功能、多少用户、多久涨多少、现有技术栈是什么。
  • ② 画大图并征得同意，10 到 15 分钟。把面试官当队友，边画边问「这样可以吗」。
  • ③ 深挖，10 到 25 分钟。先挖最关键的部件，别在小细节上耗时间。
  • ④ 收尾，3 到 5 分钟。讲瓶颈、失败情况、怎么监控和上线、再涨 10 倍怎么办。别说「我的设计很完美」。
  • 忌讳：不问就答、一上来钻细节、闷头想不说话、过度设计。卡住就要提示。

Before I jump in, I'd like to clarify scope. Then I'll sketch a high-level design and check it with you before going deeper.

第 4 章 · 限流器

会怎么问：「设计一个限流器」或者「怎么保证不把下游打爆」。

  • 放哪：客户端不可靠；放服务端，或者放在网关这一层中间件里。
  • 五种算法：令牌桶（简单省内存，允许短暂突发，两个参数不好调）；漏桶（匀速处理，突发会把队列塞满旧请求）；固定窗口（简单，但卡在两个窗口交界处能放过两倍的量）；滑动窗口日志（最准，最费内存）；滑动窗口计数（当前窗口数加上前一窗口数乘重叠比例，省内存，是近似值）。
  • 计数存 Redis：一个命令加一，一个命令设过期。
  • 规则写在配置文件里，Worker 定期读进缓存。
  • 超了：返回 429，并在响应头里告诉对方还剩几次、多久后再试。被限的请求可以丢，也可以进队列晚点处理。
  • 多台机器两个坑：并发时两个请求同时读到同一个数（用 Lua 脚本或有序集合解决）；多台限流器之间不同步（用一个集中的 Redis，别用粘性会话）。
  • 加分：硬限流对软限流；按 IP 在网络层限；客户端自己也要退避重试。

借到 Subimage：你们是「被限的那一方」。每个客户账号、每个服务、每个区域各一个桶；云厂商返回 Throttling 就指数退避并加随机；把剩余额度留一部分给客户自己的自动化。

I'd use a token bucket per account, service and region, stored in Redis with an atomic script, and back off exponentially with jitter when the cloud API throttles us.

第 5 章 · 一致性哈希

会怎么问：「加一台机器，数据怎么重新分配？」

  • 普通做法是「哈希值除以机器数取余」。机器数一变，几乎所有数据都换了位置，缓存全部失效。
  • 一致性哈希：机器和数据放在同一个环上，数据顺时针找到的第一台机器就是它的家。
  • 加减一台机器，平均只动 k/n 的数据（k 是数据量，n 是机器数）。
  • 两个问题：机器在环上间隔不均；数据可能挤在一台上。解法是虚拟节点，每台机器放很多个分身。分身越多越均匀，代价是多存一点映射。

借到 Subimage：把租户分给采集 Worker 或者分片时用它。大租户可以多给几个分身。

With consistent hashing only about k over n keys move when a node joins or leaves, and virtual nodes keep the load even.

第 6 章 · 键值存储

会怎么问：「设计一个分布式键值库」，或者追问一致性。

  • CAP：网络一定会断，所以实际是在「一致」和「可用」之间选。银行选一致（宁可报错）；大多数互联网产品选可用（先给旧数据）。
  • 分区：用一致性哈希。复制：顺时针往下找 N 台不同的机器各存一份，最好跨机房。
  • 法定人数：N 份副本，写要 W 份确认，读要 R 份回应。W 加 R 大于 N 就是强一致。常见配置 N=3，W=R=2。W 或 R 等于 1 就快但不保证最新。
  • 冲突：每份数据带一个版本记录（向量时钟），能看出两个版本是先后关系还是冲突；冲突交给客户端合并。
  • 发现故障：节点之间互相「八卦」心跳，不靠一台机器说了算。
  • 临时故障：别的节点先代收，等它回来再还（hinted handoff）。永久故障：用 Merkle 树对比两份数据，只同步不一样的那几块。
  • 写：先写提交日志，再写内存，内存满了刷到磁盘上的有序文件。读：先查内存，没有就用布隆过滤器判断在哪个磁盘文件里。

借到 Subimage：图数据是「给人看攻击路径」的，读到几分钟前的数据可以接受，所以读可以走副本。但一轮同步要么整轮生效要么不生效，不能让用户看到同步到一半的图。

For this product I'd accept slightly stale reads, but I want each sync run to appear atomically, so users never see a half-updated graph.

第 7 章 · 分布式唯一 ID

会怎么问：「多台机器怎么生成不重复、按时间有序的 ID？」

  • 多主自增（每台步长为机器数）：难扩容，跨机器不按时间有序。
  • UUID：不用协调，但有 128 位，无序，不是纯数字。
  • 发号服务器：一台数据库专门发号，简单，但它是单点。
  • 雪花算法：64 位。1 位符号，41 位毫秒时间戳（够用约 69 年），5 位机房号，5 位机器号，12 位序号（每毫秒每台 4096 个）。按时间有序，不用协调。
  • 坑：机器时钟不同步，要用 NTP 对时。

借到 Subimage：资源节点不用自己发号，直接用云厂商给的唯一名字（比如 ARN）当键，重复写才不会多出一个点。同步轮次的编号可以用时间戳。

For graph nodes I'd use the provider's own identifier as the key, so repeated writes stay idempotent. For run IDs a timestamp-based ID is enough.

第 8 章 · 短链接

会怎么问：「设计 TinyURL」。

  • 估算：每天 1 亿条，约每秒 1160 次写；读写比 10 比 1，约每秒 1.16 万次读；10 年 3650 亿条。
  • 两个接口：POST 提交长链接返回短链接；GET 短链接返回跳转。
  • 301 是永久跳转，浏览器会记住，省服务器；302 是临时跳转，每次都回来，方便统计点击。
  • 短码长度：62 个字符，7 位约 3.5 万亿种，够用。
  • 两种生成法：哈希后取前 7 位，撞了就加盐再算（要查库，可用布隆过滤器加速）；或者先发一个唯一 ID 再转 62 进制（不会撞，但能被猜出下一个）。
  • 跳转读多写少，所以前面放缓存。

I'd generate a unique ID, convert it to base 62, and serve redirects from a cache. 301 saves load, 302 keeps analytics.

第 9 章 · 网络爬虫（和 Subimage 的采集最像，重点看）

会怎么问：「设计一个爬虫」。换成他们的话就是「持续采集客户的云资源」。

  • 基本循环：给一批地址，下载，抽出新地址，放回去，重复。
  • 好爬虫的四个特点：能并行扩展、健壮、讲礼貌、容易加新类型。
  • 用广度优先，不用深度优先（太深）。但普通队列有两个问题：同一个网站的链接扎堆，会把人家打爆；不分轻重。
  • 待抓清单分两层：前面一组队列管优先级（重要的先抓）；后面一组队列管礼貌（每个网站一条队列，一个 Worker 只盯一条，两次下载之间等一下）。
  • 新鲜度：按网页更新历史决定多久重抓；重要的抓得更勤。
  • 清单太大：大部分放磁盘，内存里只留缓冲。
  • 下载优化：多台机器分片抓；缓存 DNS；机器放得离目标近；设短超时，不等慢网站。
  • 健壮：用一致性哈希分配任务；保存进度，断了能接着来；异常不能让整个系统崩。
  • 去重：对内容算哈希，见过就丢。防陷阱：限制地址长度。
  • 加新类型：做成可插拔的模块。

借到 Subimage：网站换成「客户的云账号加区域」，礼貌换成「不超过客户的接口额度」，新鲜度换成「改得勤的资源（比如权限）同步得更勤」，可插拔模块正好是 Cartography 每个数据源一个模块的做法。保存进度那条对应「一轮没跑完就不清理」。

I'd treat each account and region like a host in a crawler: its own queue, its own rate limit, a priority based on how often it changes, and saved progress so an interrupted run can resume.

第 10 章 · 通知系统

会怎么问：「设计通知系统」。换成他们的话就是「发现风险后告警」。

  • 渠道各有第三方：苹果推送、安卓推送、短信、邮件。第三方可能在某些地区不可用，所以要容易替换。
  • 最初的设计是一台通知服务器包办，三个问题：单点、不好扩、慢。
  • 改进：数据库和缓存搬出去；通知服务器多台；每种渠道一条消息队列，一种挂了不影响别的；Worker 从队列取出来调第三方。
  • 不能丢：通知先写进「通知记录表」，失败就重试。
  • 恰好一次做不到，所以按事件号去重：见过这个号就不再发。
  • 其他零件：模板；用户设置（发之前先看他关没关）；限制每人收多少条；重试几次不行就告警给开发；监控队列里积压了多少；记录打开率和点击率。

借到 Subimage：安全告警最怕两件事：漏发和刷屏。漏发靠记录表加重试；刷屏靠去重和每人每天上限。同一个风险只在「新出现」和「已解决」时各发一次。

Alerts must never be lost, so I'd persist each one before sending and retry on failure. Exactly-once isn't realistic, so I'd dedupe by event ID.

第 11 章 · 信息流

会怎么问：「设计朋友圈 / Twitter 时间线」。

  • 两条流程：发帖，和取信息流。
  • 写时扩散（推）：发帖时就写进每个好友的信息流缓存。读很快；但好友很多的人发一条要写很多份，不活跃的人白算。
  • 读时扩散（拉）：打开时现拼。不浪费；但读慢。
  • 混合：普通人推，大 V 让粉丝来拉。
  • 扩散服务五步：从图数据库取好友列表 → 从用户缓存过滤掉屏蔽的 → 把「好友列表加帖子号」放进队列 → Worker 取出 → 写进信息流缓存。缓存里只存 ID，并限制条数。
  • 取的时候：拿到一串帖子号，再去用户缓存和帖子缓存把内容补全。图片视频走 CDN。

借到 Subimage：书里这一章自己就用了图数据库存好友关系。对应到你们：每个租户的「风险列表」是每次同步后预先算好存起来，还是打开页面时在图上现查。小租户预先算，超大租户按需算。

It's the push versus pull trade-off. I'd precompute findings after each sync for most tenants, and compute on demand for the largest ones.

第 12 章 · 聊天系统

会怎么问：「设计微信 / Slack」。

  • 服务器怎么主动把消息推给客户端，三种办法：轮询（客户端隔一会儿问一次，浪费）；长轮询（连接挂着，有消息才回，回完马上再连）；WebSocket（一条双向的长连接，最常用）。
  • 服务分三类：无状态的（登录、资料）；有状态的聊天服务（每个客户端长连在某一台上）；第三方推送。
  • 服务发现：登录后由它挑一台合适的聊天服务器给客户端。
  • 存储：资料类用关系库；聊天记录量大、最近的读得多，用键值库。
  • 消息号要唯一且按时间有序：全局雪花号，或者每个会话内自增。
  • 一对一流程：发到聊天服务器 → 拿消息号 → 进同步队列 → 存键值库 → 对方在线就转到他连的那台；不在线就走推送。
  • 多设备：每台设备记住自己收到的最大消息号，上线后拉比它大的。
  • 小群：给每个成员的收件箱各放一份。
  • 在线状态：客户端每隔几秒发一次心跳，一段时间没心跳才算离线，避免网络抖一下就闪。

借到 Subimage：图更新后推给打开着的网页，用这一章的三选一。Worker 是否活着，用心跳判断。

For pushing updates to the browser I'd compare polling, long polling and WebSockets, and pick the simplest one that meets the freshness need.

第 13 章 · 搜索自动补全

会怎么问：「设计搜索框的输入提示」，也叫「最热的前 k 个查询」。

  • 估算：1000 万日活，每人 10 次搜索，每次约 20 个字符，每打一个字发一次请求，约每秒 2.4 万次。要求 100 毫秒内返回。
  • 数据结构是前缀树。光有树不够快，两个优化：限制前缀最长长度；每个节点直接存好这个前缀下最热的 5 个词。这样查询是常数时间，代价是多占空间。
  • 数据不实时改：搜索日志 → 聚合器按周汇总 → Worker 重建整棵树 → 存库 → 加载进缓存。
  • 查询链路：负载均衡 → API 服务器 → Trie 缓存。浏览器也缓存结果（比如一小时）。日志可以抽样记录。
  • 删违规词：缓存前面加一层过滤，库里的异步删。
  • 树太大要分片：按首字母分不均匀，所以按历史数据分布来分，用一个分片映射表记录。
  • 追问：多语言用 Unicode；不同国家建不同的树；突发热词要给最近的数据更高权重，用流式处理。

借到 Subimage：在图里搜资源名字时的输入提示。更重要的是这章的思路：把「贵的计算」放到离线定期做，在线只查现成的结果。

The key idea is to precompute offline and serve from memory: a trie with the top results cached on every node.

第 14 章 · 视频网站

会怎么问：「设计 YouTube」。

  • 范围先砍到两条：上传和播放。尽量用现成的云服务（对象存储、CDN），别从零造。
  • 上传：视频进原始存储 → 转码服务器取出来转成多种格式和清晰度 → 转好的进转码后存储并分发到 CDN → 同时往「完成队列」发事件，处理器更新元数据库和缓存。上传文件的同时，客户端并行提交标题这些元数据。
  • 播放：直接从离用户最近的 CDN 节点流式播放。
  • 转码用 DAG（有向无环图）描述任务：检查、转码、缩略图、水印，可并行。架构六块：预处理器、DAG 调度器、资源管理器（任务队列、Worker 队列、运行队列、任务调度器）、任务 Worker、临时存储、输出。
  • 优化：把视频切成小段并行上传，断了能续传；上传点设在离用户近的地方；各环节之间用消息队列解耦；用预签名地址保证只有授权用户能传；只把热门视频放 CDN 省钱。
  • 出错：能恢复的（某段转码失败）重试；不能恢复的（文件格式坏了）停掉并返回错误。

借到 Subimage：你在 TikTok 做过 Go 的 DAG 引擎，这一章的 DAG 调度是你的主场。同步模块之间有依赖（先同步账号和权限，再同步机器和它们的关系），可以画成 DAG 让调度器按阶段发任务。

I'd model the sync modules as a DAG, since some depend on others, and let a scheduler dispatch stages to workers. I built something similar on a Go DAG engine at TikTok.

第 15 章 · 网盘

会怎么问：「设计 Google Drive / Dropbox」。

  • 功能：上传下载、多设备同步、看历史版本、分享、文件变化时通知。非功能：不能丢数据、同步快、省流量。
  • 从一台机器讲起：Web 服务器、元数据库、一个存文件的目录。满了以后把文件搬到 S3（可跨区域复制），再加负载均衡，把元数据库独立出来。
  • 同步冲突：两个人同时改同一个文件，先到的生效，后到的拿到两个版本自己选。
  • 块服务器：把文件切成块（参考值每块最大 4MB），压缩、加密后存云存储。文件改了只传改动的块（增量同步）。
  • 元数据要强一致，所以用关系库；写库时让缓存失效。
  • 通知服务用长轮询而不是 WebSocket：因为只需要服务器单向告诉客户端「有变化，来拉」，而且不频繁。
  • 省空间：相同的块只存一份（按哈希判断）；限制保留的版本数；很久没人看的进冷存储。
  • 失败处理：每个部件挂了怎么办都要能说出来，无状态的换一台，有状态的靠副本。

借到 Subimage：「时间旅行」直接借这一章：版本表只追加不修改；每轮同步只记录变化的点和线，而不是整张图再存一份；旧版本压缩后进便宜的存储。「增量同步」对应只重写哈希变了的资源。

For time travel I'd borrow from file versioning: append-only version records, store only what changed in each run, and move old history to cheaper storage.

第四部分 · 估算和万能句

估算怎么做（书第 2 章的流程），用 Subimage 的例子

  • 假设 200 家客户，一家大的有 50 万个资源，平均 5 万个。总共约 1000 万个点。线大约是点的 3 到 5 倍，也就是 3000 万到 5000 万条。
  • 每个资源算 1 KB，1000 万个点约 10 GB。一台 Neo4j 装得下，所以先不用分片。这句话值得说出来。
  • 每小时全量同步一次：1000 万次写除以 3600 秒，约每秒 3000 次，高峰按两倍算 6000 次。批量写（一次几千条）没有问题。
  • 真正的瓶颈不在数据库，在云厂商的接口限速。所以设计重点放在限流和并行上。

Roughly ten million nodes and tens of millions of edges. That fits on one machine, so I wouldn't shard yet. The real bottleneck is the cloud APIs' rate limits, not the database.
