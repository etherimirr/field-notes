AI Agent 时代的五张「图」

Ontology / Knowledge Graph / Context Graph / Code Graph / Graph Engineering

一句话总纲
前四张回答「系统知道什么」，第五张回答「系统怎么干活」。

1. Ontology（本体）—— 规则书

组织的「标准术语表 + 家规」。不记录具体的人和事，只规定概念如何定义、实体之间允许存在什么关系、哪些规则永远成立。 相当于字典和语法书的合体，严格到机器可读。

核心价值是统一语义口径，让多团队多系统对齐；并且能让系统自动推理出新结论（例如从既有关系推出「某药可治某病」）。 金融、医药领域有成熟的开源本体可直接用。

2. Knowledge Graph（知识图谱）—— 世界网

照着本体的「规范」盖出来的房子：把真实的人和事填进去，织成一张 「谁—什么关系—什么」 的网。 像一本长了神经的百科全书，既能查条目、也能顺着关系一路问下去。

适合常识问答与推荐。短板：它只知道「全世界普遍为真的事」，不知道某个组织此刻正在发生什么。

3. Context Graph（上下文图谱）—— 任务上下文地图

在知识图谱基础上叠加任务、状态、事件、历史决策，形成面向 agent 决策的「业务上下文地图」， 回答的是 「当前为什么重要、该怎么做决策」。

分三层：① 语义基础　② 运行元数据（数据血缘、质量、权限）　③ 决策轨迹。
适用场景：agent 正式接手业务前的可信上下文构建、影响分析、审计合规追溯。
这一层是 demo 级和企业级 agent 的分水岭。
多数个人项目把「agent 做过什么决定、为什么这么决定」留在日志里。 把决策轨迹变成可查询的结构，是最能拉开差距的一步。

4. Code Graph（代码图谱）—— 代码内部管网图

把软件系统画成一张可查询的图：函数、类、模块是节点；谁调用谁、数据怎么流、谁继承谁是边。 改代码前先顺着图看「下游谁会受影响」。适合大型代码库的关系梳理与风险预演。

5. Graph Engineering（图谱工程）—— Agent 的轨道

和前四张完全不同 —— 它回答「怎么干活」。

本质是给大模型装上轨道：入口处让 agent 自己判断，其余路段按既定轨道走，既保留自由度又保证可靠性。 包含数据工程、图谱建模、检索、推理、agent 编排等要素。适合有固定套路的业务流程和多 agent 协同。
这句话顺带回答了一个常见问题：为什么要用图编排框架，而不是让模型自由循环。

领域映射

来源作者给的对照：做医疗 AI 的会更多用到 Ontology + FHIR；做电商推荐的则 Knowledge Graph + Context Graph 更关键。
