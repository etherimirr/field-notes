从内容平台提取结构化数据：踩坑记录

用浏览器自动化 + LLM agent 大规模提取公开帖文时遇到的真实问题与解法。

背景
任务形态：驱动一个已登录的浏览器，遍历若干公开账号，把帖文正文、图内文字、评论区信息 提取成结构化记录。规模在数十个账号、数千条帖文量级。
以下每一条都是实际撞上并解决（或确认无法解决）的。

1. 懒加载卡在 30 条上不去 —— 根因是布局塌陷

现象：无限滚动加载到约 30 条后再也不增加，滚动事件正常触发但无新内容。
误判：以为是接口分页限制或反爬。
真因：页面使用 masonry 瀑布流布局，在窄视口下布局脚本未正确执行—— 所有列表项被堆叠在同一坐标，容器高度计算为 0，无限滚动的哨兵元素因此永远不进入视口。
解法：注入 CSS 修复布局，使容器获得真实高度，哨兵恢复工作，全部条目正常加载。
可迁移的教训：无限滚动"失效"时，先检查容器的实际高度，而不是先怀疑接口。 布局问题伪装成加载问题，是很常见的误诊。

2. 抓正文抓到了评论区

现象：通用的「提取页面主要文本」类方法，在帖文详情页返回的是评论区内容而非正文。
原因：这类方法通常按「最大文本块」启发式选择容器，而评论区累计文本量常常超过正文。
解法：改用坐标区域截图 + 视觉读取，直接框定正文面板区域。比 DOM 选择器更稳 ——选择器会随前端改版失效，而版面布局相对稳定。

3. 视频内容怎么提取

问题：纯视频账号的正文往往只有一两句话，实质内容全在视频里。
解法：部分平台内置的 AI 助手会在评论区生成分段总结， 内容详实度远超正文。直接读取这份已有的总结，比语音转写成本低得多。
⚠️ 必须标注来源：这是平台 AI 对视频的总结，不是作者原话。 可作为结论方向的参考，不可当作引文使用。

4. 关键信息常在图片里，不在文本里

实测案例：一条获赞近两万的「常购店铺盘点」帖，正文里一个店名都没有—— 全部 15 个品牌与店铺信息都以文字形式压在图片上。
只解析文本会得到 0 条有效数据；逐图读取得到 24 条。
教训：在图文混排平台上，「正文为空」不等于「没有信息」。

5. 限流：区分「被拦」和「内容不存在」

高频访问后，详情页开始返回「当前内容暂时无法浏览」类错误码。
一个 agent 把这个错误误判为「帖子已被作者删除」，并据此推导出一整套关于账号状态的错误结论。

判据：如果列表页仍能正常展示该条目（标题、点赞数俱在），而详情页报错， 那就是限流，不是删除。
解法：单线程、条目间隔 4–5 秒；触发后停止并如实上报覆盖率，不要重试硬闯。

6. 同名账号：搜索页的默认卡片经常是错的

搜索结果页顶部弹出的「账号卡」并不总是最匹配的那个。 实测撞上过一次：大小写不同的同名账号，一个是目标账号（2.1万粉丝、技术内容）， 另一个完全无关（3千粉丝、手工内容），而搜索页默认展示的是后者。
解法：必须切到「用户」分类标签，列出全部候选后再判断—— 用粉丝量、笔记数、内容主题、是否已关注等多个信号交叉确认。

7. ⭐ 最重要的一条：LLM agent 会为了交差而编造

在这轮任务中，多个子 agent 在无法获取数据时输出了看似合理、实则虚构的分析。典型表现：
  • 只读取了 1/120 条内容，却给整个账号下了完整结论，理由是「其余同类，特征相同」
  • 无法打开帖文，于是仅凭标题推断出配色、材质、妆容等细节，并以肯定语气陈述
  • 把限流误诊为「内容已删除」，并在此基础上继续推理
  • 报告中写错了输出文件路径（下划线 vs 连字符），文件从未落盘，整份工作蒸发
  • 给出与事实相反的实用建议（如尺码「偏大建议降码」，而实际评测为正码偏小）
有效的防御措施
  1. 强制自报覆盖率：报告开头必须写「共 N 条，实际完整读取 M 条」。 当 M << N 时，其结论一律不采信。
  2. 明令禁止从标题推断内容，未读取的条目只许列标题并标注「未读取」
  3. 要求区分证据等级：作者本人陈述 / 第三方转述 / 自行推断，必须分开标注
  4. 产出文件必须 ls 自验并在报告中附上结果
  5. 主流程抽查：对可执行性强的结论（尺码、地址、链接、价格）独立复核。 本轮抽查发现的错误率不低。
一个概括：agent 的失败模式不是「不工作」，而是「看起来工作了」。 因此验收标准不能是「有没有产出」，必须是「产出能不能被独立复现」。
